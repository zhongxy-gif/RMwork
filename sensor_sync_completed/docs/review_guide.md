# 传感器同步项目 - 复习笔记

> 通俗易懂版复习整理
> 
> 想象一个场景：**快递分拣中心**
> - 相机 = 一类快递包裹
> - IMU = 另一类快递包裹
> - 队列 = 传送带
> - 生产者 = 两种包裹的卸货员
> - 消费者 = 分拣员（按类型把包裹分到不同区域）
> - 时间戳同步 = 给每个相机包裹找一个"时间最接近"的 IMU 包裹做配对

## 一、这个项目到底在干什么？

RoboMaster 机器人有很多传感器：相机、IMU（陀螺仪+加速度计）。它们同时工作，但**数据频率不同、到达时间也不同**。

举个例子：相机 1 秒来 30 帧，IMU 1 秒来 200 条。我们需要让每个相机帧"找到"它拍摄时刻最接近的 IMU 数据，这样才能把视觉和姿态信息对齐。

**项目任务**：
1. 模拟两路传感器数据（用文本文件代替）
2. 用多线程同时读取两路数据
3. 放到一个共享队列里
4. 按时间戳配对

## 四、核心概念通俗解释

### 4.1 什么是线程？

想象两条**同时工作的流水线**。程序本来是一条流水线（主线程），用 `std::thread` 可以多出几条。

```
主线程：  [读配置] → [开三个线程] → [等它们干完] → [配对数据] → [写结果]
相机线程： [读 camera.txt] → [把数据放到队列]
IMU线程：  [读 imu.txt] → [把数据放到队列]
消费者线程：[从队列拿数据] → [按类型分开存放]
```

### 4.2 什么是互斥锁 (mutex)？

队列是共享资源，两个生产者同时放数据可能会出问题。`std::mutex` 就像一把**门锁**：同一时刻只有一个线程能拿到锁，其他线程在门口等。

```
线程A：[加锁] → [放数据] → [解锁]
线程B：..........在门口等..........  → [加锁] → [放数据] → [解锁]
```

### 4.3 什么是条件变量 (condition_variable)？

如果队列满了，生产者不能傻等（CPU 占用 100%）。`condition_variable` 让线程**睡觉**，等消费者拿走数据后再**叫醒**它。

```
生产者：  队列满了... 睡觉 💤
消费者：  拿走一个数据 → 通知生产者"有位置了！" → 生产者醒来 ✅
```

### 4.4 什么是线程安全队列？

就是一个**带锁的队列**，内部用 mutex + condition_variable 保证：
- 多线程同时 push/pop 不会出错
- 队列满时 push 会阻塞等待
- 队列空时 pop 会阻塞等待
- 关闭后不再接受新数据

## 五、线程安全队列详解

### 5.1 队列内部结构

```
ThreadSafeQueue
├── capacity_    容量（比如8）
├── queue_       实际存数据的双端队列
├── closed_      关闭标志
├── mutex_       锁
├── not_empty_   通知"有数据了"（叫消费者起床）
└── not_full_    通知"有空位了"（叫生产者起床）
```

### 5.2 push（生产者放数据）

```
生产者调用 push(数据)
  │
  ▼
🔒 加锁
  │
  ▼
队列满了吗？
  ├─ 是，而且没关闭 → 💤 睡觉，等消费者通知
  └─ 否 → 继续
  │
  ▼
队列关闭了吗？
  ├─ 是 → 解锁，返回 false（放不了了）
  └─ 否 → 继续
  │
  ▼
数据入队
  │
  ▼
📢 通知消费者："有数据啦！"
  │
  ▼
🔓 解锁，返回 true
```

### 5.3 pop（消费者拿数据）

```
消费者调用 pop(变量)
  │
  ▼
🔒 加锁
  │
  ▼
队列空了吗？
  ├─ 是，而且没关闭 → 💤 睡觉，等生产者通知
  └─ 否 → 继续
  │
  ▼
队列还是空的？
  ├─ 是（说明已关闭）→ 解锁，返回 false（没数据了）
  └─ 否 → 继续
  │
  ▼
数据出队
  │
  ▼
📢 通知生产者："有空位啦！"
  │
  ▼
🔓 解锁，返回 true
```

### 5.4 close（关闭队列）

```
主线程调用 close()
  │
  ▼
🔒 加锁，设置 closed_ = true，🔓 解锁
  │
  ▼
📢 通知所有等待的线程（生产者+消费者全叫醒）
```

**关键理解**：关闭 = "不会再有新数据了"，不是"清空队列"。队列里已有的数据还是能被消费。

### 5.5 为什么用"等待+条件"而不是 while 循环？

```
❌ 傻等（忙等）：
while (queue.full) {
    // CPU 占用 100%，电脑卡死
}

✅ 聪明等（条件变量）：
not_full_.wait(lock, [&]{ return !queue.full; });
// 线程睡觉，不占用 CPU
// 条件满足后自动醒来
```

## 六、主程序流程

```
[程序开始]
  │
  ▼
读取配置文件 sensor_sync.conf
  │  里面写着：队列容量、文件路径、最大时间差
  │
  ▼
创建 ThreadSafeQueue（容量=配置里的值）
  │
  ▼
同时启动 3 个线程：
  │  📷 相机线程：读 camera.txt，把每个数据包 push 到队列
  │  📐 IMU线程：  读 imu.txt，把每个数据包 push 到队列
  │  🔍 消费者线程：不断从队列 pop，按类型分别存到 cameras/imus 列表
  │
  ▼
等待两个生产者线程结束（join）
  │  此时确定：不会再有新数据了
  │
  ▼
关闭队列（close）
  │  告诉消费者："没新数据了，处理完剩下的就退出吧"
  │
  ▼
等待消费者线程结束（join）
  │  此时确定：所有数据都处理完了
  │
  ▼
调用 synchronize() 做时间戳配对
  │
  ▼
把结果写入 data/result.txt
  │
  ▼
[程序结束]
```

### 为什么要按这个顺序 join？

```
正确顺序：生产者 join → close → 消费者 join

如果先 close 再 join 生产者：
  生产者 push 时发现队列已关闭 → 数据丢失！
  消费者可能提前退出 → 队列里还有未处理的数据！
```

## 七、时间戳同步算法（核心！）

### 7.1 输入数据长什么样？

camera.txt:
```
0 1000      ← 序号0，时间戳1000微秒
1 2000      ← 序号1，时间戳2000微秒
2 3000
3 5000
...
```

imu.txt:
```
0 800
1 1200
2 1900
3 3100
...
```

每行格式：`序号 时间戳(微秒)`

### 7.2 配对规则

对每个相机包，找一个时间最接近的 IMU 包：

```
规则（按优先级）：
1. 时间差 <= max_delta_us（默认300微秒）→ 配对成功
2. 时间差相同 → 选时间戳更早的 IMU
3. 时间戳也相同 → 选序号更小的 IMU
4. 时间差 > max_delta_us → UNMATCHED（配对失败）
5. 一个 IMU 可以被多个相机配对
```

### 7.3 双指针算法（大白话版）

**核心思想**：排好序后，每个相机要找的 IMU 肯定在"附近"，不用全表扫描。

```
第一步：把相机和 IMU 各自按时间戳排序

相机（排好序）：
  C0(1000)  C1(2000)  C2(3000)  C3(5000) ...

IMU（排好序）：
  I0(800)  I1(1200)  I2(1900)  I3(3100) I4(4200) ...

第二步：用两个指针同步前进

指针 right 指向：IMU 中第一个时间戳 >= 当前相机的位置

处理 C0(1000)：
  right 指向 I1(1200)  ← 第一个 >= 1000 的 IMU
  检查 I1(1200)：差 |1000-1200| = 200
  检查 I0(800)：  差 |1000-800|  = 200
  两个一样近，选更早的 I0 → 匹配成功，DELTA 200

处理 C1(2000)：
  right 前进到 I3(3100)  ← 第一个 >= 2000 的 IMU
  检查 I3(3100)：差 |2000-3100| = 1100
  检查 I2(1900)：差 |2000-1900| = 100  ← 更近
  → 匹配成功 I2，DELTA 100

处理 C3(5000)：
  right 前进到 I5(6300)
  检查 I5(6300)：差 1300
  检查 I4(4200)：差 800
  800 > 300（超过限制）→ UNMATCHED
```

### 7.4 为什么只看"前后两个"就够了？

因为数据是排好序的。假设当前相机时间戳是 5000，IMU 时间戳是 4200、6300。距离 5000 最近的只能是 4200（前面最后一个）或 6300（后面第一个）。不可能是 3100，因为 3100 比 4200 还远。

**时间复杂度**：O(C log C + I log I + C + I)
- 排序：C log C + I log I
- 遍历：C + I（双指针不会回溯）

### 7.5 三级"打破平局"规则详解

```
相机时间戳 = 2000，两个候选 IMU 时间戳都是 1900：
  → 平局1：时间戳相同 → 比序号

相机时间戳 = 2000，IMU-A(1900, seq=3) vs IMU-B(1900, seq=5)：
  → 时间戳相同 → 选序号更小的 A

相机时间戳 = 2000，IMU-A(1800) vs IMU-B(2200)，时间差都是 200：
  → 平局0：时间差相同 → 选时间戳更早的 A
```

## 九、常见问题 FAQ

### Q1：程序运行了但没反应？

正常！程序会默默处理数据，然后：
- 结果写入 `data/result.txt`
- 终端打印 `Done. Result written to data/result.txt`

### Q2：`./build/sensor_sync config/sensor_sync.conf` 是什么意思？

- `./build/sensor_sync` = 运行编译好的程序
- `config/sensor_sync.conf` = 告诉程序配置文件在哪

### Q3：队列的 push/pop 会循环吗？

不会。它们是**条件阻塞**：队列满了生产者就"睡觉"，队列空了消费者就"睡觉"，等有空间/数据时自动"醒来"。不浪费 CPU。

### Q4：关闭队列后还能取数据吗？

能。`close()` 的意思是"不再接受新数据"，不是"清空数据"。队列里已有的数据还能正常取走。

### Q5：为什么配置文件里写 `../data/camera.txt`？

因为配置文件在 `config/` 目录下，路径是相对于配置文件位置的。`../data/` 就是从 `config/` 往上一级到项目根目录，再进 `data/`。

### Q6：一个 IMU 能被多个相机配对吗？

能。规则说"同一个 IMU 包允许匹配多个相机包"。

### Q7：数据文件里的数字代表什么？

- 第一个数：序号（第几个数据包）
- 第二个数：时间戳（微秒，1秒 = 1,000,000 微秒）

### Q8：`max_delta_us=300` 是什么意思？

如果相机和 IMU 的时间差超过 300 微秒（0.3 毫秒），就认为"差太远了，不配对"，输出 UNMATCHED。

## 十、考试速记卡片

### 🔑 三个必须记住的 C++ 组件

| 组件 | 用途 | 一句话说明 |
|------|------|-----------|
| `std::thread` | 多线程 | 同时干多件事 |
| `std::mutex` | 互斥锁 | 同一时刻只有一个线程能用共享数据 |
| `std::condition_variable` | 条件变量 | 线程没事做时先睡觉，有事再叫醒 |

### 🔑 队列核心逻辑

```
push  → 满了就等，关了就放弃
pop   → 空了就等，关了+空了就放弃
close → 叫醒所有人，宣布"不再接收新数据"
```

### 🔑 线程生命周期

```
生产者 join → close → 消费者 join
（必须这个顺序！）
```

### 🔑 同步算法核心

```
1. 相机和 IMU 各自按时间戳排序
2. 双指针：每个相机只比较"前后两个"IMU 候选
3. 三级打破平局：时间差 → 时间戳 → 序号
4. 超过 max_delta_us → UNMATCHED
```

### 🔑 算法复杂度

```
O(C log C + I log I + C + I)
排序开销        遍历开销
```

### 🔑 输出格式

```
匹配成功：CAMERA <相机序号> IMU <IMU序号> DELTA <时间差>
匹配失败：CAMERA <相机序号> UNMATCHED
```
